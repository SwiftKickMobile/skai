Design ui-map-chg-mgmt

discussion complete

Update the UI Map designs for change packages, for the change management style in skai#101, where a UI Map change request is authoring against a different base. The code follows later.

Discussion

Highlighting Changes

D01QuestionHow can the UI Map highlight changes?resolved
  • Concern A change package's map page shows the proposed map alone, so a reviewer can't see on the map what the package changes.
  • Question How should the map show what changed? To be discussed with the supervisor.
  • Decision Changed scenes get a special icon or styling on the proposed map, and selecting one opens the side panel with its entries from the change list. A scene counts as changed when anything about it changes or anything about its outgoing connections changes. There is no true comparison view, because a map can change in too many ways to show them all.

Review Page

D02QuestionHow can a UI Map package get a review page similar to the one for designs?resolved
  • Concern Design packages have a review page for their discussion and list of changes. A UI Map package has only its map page and a markdown document.
  • Question What should a UI Map review page look like, and how does it relate to the map page? To be discussed with the supervisor.
  • Decision The discussion and changes are another tab on the map page, named Review, not a separate page.
D03ProposalThe tab and the map link to each otherresolved
  • Concern A reviewer reading a change in the tab has no direct way to see it on the map, and a reviewer reading an entry in the side panel has no direct way to see it among the other changes and the discussion behind it.
  • Proposal Each scene a change touches is a link that switches to the map tab and selects that scene. Each entry in the side panel links to that change in the tab.
  • Why The two views answer each other's next question, and the links add little to either one. The alternative is no links, which is simpler, but the reviewer then has to find the scene or the change by hand.
  • Decision The tab groups changes by domain, with each domain's color square on its heading, and each entry's header names its scene as a link to the map, the way a design change's header links to its frame. Each entry in the side panel links to that change in the tab. A connection change names the scene it starts from, a domain change names its domain with no link, a moved scene sits under its new domain, and a removed scene sits under its old domain with its name greyed and no link.

Page Titles

D04ProposalEvery change package's page uses one title formatresolved
  • Concern The specs review pages don't say which artifact they review, the design review repeats its name on a second line, and the UI Map change page leads with the app's name.
  • Proposal One line on every page: the package's ID in black, then the artifact type in cyan, such as note-versions UI Map Change or pinned-notes Design Change. The production map keeps LumenNotes UI Map, which has the same two colors.
  • Why A reader most needs to know which artifact and which package they're looking at. Color separates the two more cleanly than a colon or a second line, and each color means the same thing on every page.
  • Decision One line on every change package's page: the document type in black, then the package's ID in cyan, such as UI Map note-versions or Design pinned-notes. The word Change is dropped because every one of these pages is a change document. The production map follows the same format as UI Map Production, so its bar no longer shows the app's name.

Review Page Styling

D05ProposalThe real review pages set the styling for review pages and the UI Map pageresolved
  • Concern The backfill restyled the review pages' designs to match the UI Map, so they no longer match the real pages, whose typography, spacing and cards read better.
  • Proposal The real review pages' typography, spacing and cards become the design, on the light blue-grey background. The UI Map page's top bar, side panel, cards and help take the same styling, while map cells, route boxes and route labels stay compact.
  • Why Reviewers read these pages at length, and one look across SKAI's pages is simpler to build and maintain.
  • Decision Adopted as proposed. The whole page moves to the system font, including map cells; IDs and route kinds stay monospace. The real review pages also take the mockups' colors, plain cyan references, colored changed words and 56 top bar height.

  • 01 — The map on a change package's page marks each changed scene with a badge set into its bottom right corner, in the same color as the scene's border.   • 02 — The top bar's title becomes UI Map followed by the package's ID, and the bar gains Map and Review tabs.
Why A reviewer needs to see on the map where the package changes it, and no comparison view could show every kind of change. Source: Resolved decision: D01.
addedV22add stateui map — changes on

A single-item Changes toggle sits to the right of the domain filters, showing how many scenes changed. Turning it on displays changed scenes the way search displays its matches: changed scenes are highlighted, and everything else is dimmed. It follows search's rules with other controls: it doesn't show the hops drop-down, and while a selected scene or domain filter narrows the map, nothing is dimmed.

Why A reviewer can pick out every changed scene at a glance on a large map. Source: Supervisor input.
addedV02add stateui map — changed scene selected

Selecting a changed scene opens the side panel with a Changes section first, headed by the change icon, listing that scene's entries from the change list. Each entry's ID links to that change in the Review tab. An entry with several changes numbers them, as in the design review. Section heading icons, including the Note heading's, match their heading's color, and the Reached from and Opens headings lose their counts.

Why The panel answers what changed here at the moment the reviewer asks, and the link leads to the other changes and the discussion behind them. Source: Resolved decision: D01 and D03.
addedV03add stateui map — changes help

How to read this map gains a row explaining the change badge, after the three scene styles and before the icons, shown on a change package's page. Its instructions no longer mention a Clear button, on the production map as well, and explain the Changes toggle on a change package's page.

Why The help explains everything else drawn on a scene, and a new mark needs the same explanation. Source: Resolved decision: D01.
addedV14add stateui map — production top bar

The production map's top bar, titled UI Map Production, with domain filters in the review pages' style: a bordered group of filters, each with its domain's color, its number of scenes and its name. It replaces the plain row of names, moves to the right of the bar as the review pages' filters are, and applies to every state of the production map.

Why The filters on the UI Map and the review pages should look and work alike. Source: Supervisor input.

The hops control is a drop-down showing the current choice. Opening it lists 1 hop, 2 hops and All, with the current one marked. This applies to the production map as well.

Why A drop-down takes less room in the top bar than a segmented control now that the domain filters are grouped beside it. Source: Supervisor input.

Review

addedV04add screenui map — review

The whole Review tab, as tall as its content: the summary box, the discussion, then Map Changes grouped by domain, with each domain's color square on its heading, and otherwise laid out like the design review's Design Changes. Each entry's header shows its marker, ID, type and the scene it belongs to, as a link to that scene on the map. A connection change names the scene it starts from, a domain's own change names the domain with no link, a moved scene sits under its new domain, and a removed scene sits under its old domain with its name greyed and no link. An entry with several changes numbers them, and an entry resting on an open gap carries a numbered footnote with the gap's placeholder. The summary box shows the state and goal. The top bar's filters cover added, modified, removed and moved changes, and the discussion states the package has, among open, gap and resolved.

Why A reviewer can read the changes in the same order as the map, and go from any scene to the map. The layout follows the design review page, which a reviewer already knows, with the real review pages' typography, spacing and cards. Source: Resolved decision: D02, D03 and D05.
