# Release 13 — 2026-10-14

**Design specs**

- 2026-10-13 **Design specs: a new building block.** A design spec joins a screen's design to the requirements: which drawn state shows under which condition, how data is formatted, which copy varies with state or data, what each control does, where the screen leads. Four guides under `Guides/DesignSpecs/`, modeled on the requirements block; addendum lookup names are the file stems. New manifest category `Design specs`.
- 2026-10-13 **Content guide `design-specs.md`.** Layout `design-specs/{screens,shared,global}/` with a root index and a glossary that is the second index; items `### UI-<PREFIX>-<NN>` with bold two-digit rule segments, cited by path `UI-NOTES-01.03`; file-independent, append-only IDs with `move`; product language only, never appearance, copy owned by the design, mechanism is the developer's, no restatement of requirements; the ten verification checks V1–V10 that authoring and promotion share.
- 2026-10-13 **Authoring, promotion and artifacts guides.** `design-specs-authoring.md`: change package at `skai/changes/<change-id>/design-specs/`, inferred mode, one Discussion gate, design-vs-app differences and undrawn states as Discussion items, requirements gaps seeded as a sibling requirements package. `design-specs-promotion.md`: readiness screen, C1 verification, C2 destination links, C3 write, C4 archive to `skai/promoted/<change-id>/design-specs/`. `design-specs-artifacts.md`: spec change items `S<n> <add|modify|retire|move> <object>: <identity>` with inline diffs; change requests at `change-requests/design-specs-<nnn>.md`. The maintainer reference `internal/maintenance/change-packages.md` now lists `design` and `design-specs` as package types.
- 2026-10-13 **Skills `skai-design-specs-authoring` and `skai-design-specs-promotion`** (thin wrappers, all three adapters). **Installation:** on a configured host the update offers them as new components; a default host installs them.

**Artifact location**

- 2026-10-13 **Resources are found through the project README.** The shared agent instruction block (`Templates/agents/instructions-block.md`) now opens with: read `README.md` first; it links the project's resources, and a linked resource is where the README says it is. A resource a task needs that is not linked is unavailable even when something else names it: stop at a blocked gate; do not look for it. No other guide looks resources up or says where they live: the requirements catalog guide's *Repository shape* section, the Figma guide's *Where the file is listed* section, and the location sentences and blocked gates in requirements, design and design-specs promotion, design authoring, UI Map implementation, work-spec creation/implementation and dev retro are gone; the `local | shared | none` vocabulary is gone. Removed: `Templates/docs/skai/integration-sections/requirements.md`, the `Section: requirements` markers in the Integration template, its manifest entry and the installer step that filled it (`Install/integration-doc-install-update.md` step 4 now says what replaces it). **Migration:** re-run the installation update: it refreshes the instruction block in `CLAUDE.md` / `AGENTS.md` / Cursor rules, and proposes removing the `requirements` managed block from `skai/integration.md` as legacy cleanup (permission-gated) after confirming the README links the catalog at the root the block named, or proposing that link.
- 2026-10-13 **Artifacts live under `skai/`.** The requirements catalog and the design specs have fixed roots `skai/requirements/` and `skai/design-specs/`, beside `skai/ui-map/`, each in whichever repository the supervisor names for it; the Layout trees in `requirements-catalog.md` and `design-specs.md` and the evidence examples in `requirements-promotion.md` show the roots. **Migration:** move each existing root (`requirements/` → `skai/requirements/`, `design-specs/` → `skai/design-specs/`) with `git mv`, contents unchanged. Links between the two artifacts keep their depth; links from packages under `skai/changes/` and `skai/promoted/` and from the project README change by one `../`: search those for `requirements/` and `design-specs/` targets, repoint them, update the README link to the new root, and verify every link definition resolves.
- 2026-10-14 **New guide `Guides/Core/artifact-hosting.md`** (manifest `guide.artifact-hosting`; addendum lookup name `artifact-hosting`), read when an artifact does not exist yet. The supervisor names the repository that holds it, never inferred, and the README link is added when the package is created, pointing at the final location. It suggests a README entry shape (name, link, description) for a README with no format of its own, with the test a description must pass (a reader who has not opened the artifact can tell from it alone whether their question is answered there); a repository column is optional. The artifact is linked from the README the agent reads and also from its own repository's README when that is a different repository. The requirements, design-specs and UI Map architecture authoring guides point at it with one sentence. Standard: `skai/refinement-reviews/artifact-location-design.md`. **Migration:** where an artifact lives in a context repository, add the entry to that repository's README if it is missing.
- 2026-10-13 **No package discovery.** Guides no longer scan `skai/changes/` for packages or block on multiple candidates; the package is the one named or already in context. Removed from requirements, design-specs, UI Map and design authoring and promotion, UI Map implementation, and the dev retro, which now reads only the open packages supplied or used in the session. The design-specs next-ID rule counts canon only; a collision between two packages is caught by `V8` when the later one promotes. No host migration.

**Design**

- 2026-10-14 **Multiple sizes: chrome content is set on each size-page instance.** `figma-designer-guide-multiple-sizes.md` rule 5 said content set through component properties survives the `target` variable switching the chrome's variant; it doesn't when the values are set only in the screen component. The rule now has the chrome's properties (title, selected tab, and so on) set again, to the screen component's values, inside each screen instance on a size page. **Migration:** in a Figma file with more than one target size, check each screen instance on the further size pages: where its chrome shows component defaults instead of the screen's values, set those properties inside the instance. Single-size files are unaffected.
- 2026-10-13 **Design package `evidence/`.** `design-authoring.md` lists `evidence/` in the package table, and the promotion example keeps check output inside `skai/changes/<change-id>/design/`, the folder `C6` archives. **Migration:** a design package holding evidence at `skai/changes/<change-id>/evidence/` moves it under its `design/` folder and repoints the evidence links.

**Installation**

Overrides are visible without expanding: an overridden component's name and its category's name are blue on both tabs; the Project tab keeps its **User: On/Off** label and the User tab's **Project: On/Off** label is gone. Same config files and JSON events. **Hosts:** nothing to do; the app is read from the SKAI checkout.
