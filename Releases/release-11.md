# Release 11 — 2026-10-10

- **Configure SKAI.** Add the always-available `skai-configure` skill and repo-bundled Apple Silicon app for macOS 13 or later. Its Project/User tabs show categorized components, parent descriptions, three-state private overrides, override counts and counterpart badges; inherited User labels are dimmed and bulk actions use an ellipsis menu.
- **Save and handoff.** Explicit `--agent-session` mode uses Save and Apply, closes and resumes the waiting agent. Standalone Save stays open with manual apply instructions; direct launch discovers the owning submodule host or offers a picker. Save is enabled only for changed drafts, preserves unrelated keys and unchanged layers, and blocks stale input. Native and portable resolvers enforce the same integer schema version.
- **Configuration-driven installation.** All three adapters reconcile actual managed outputs on every invocation, including unchanged SHAs. Project selections and sparse private overrides control eligible components; defaults apply when project config is absent, and explicit empty selection retains configure support. Selected wrappers reference the actual checkout path, including non-default locations.
- **Component migration history.** Customization or any managed removal starts a full per-adapter component ledger before outputs are removed. Disabled and retired components retain their last applied versions for catch-up migrations, including same-SHA re-enablement; local effective choices/history remain private. Successful state is recorded only after artifact migrations and inventory verification.
- **Update recovery and authority.** Compare actual checkout HEAD independently of installed versions; discover local, shared, then legacy installation state. Legacy Claude identity conversion preserves evidence through verified success, and global fallback requires the sole matching adapter. Scoped Save/explicit apply approval avoids duplicate confirmation; configuration drift beyond that scope uses the existing approval route.
- **Project guide addenda.** Every registered guide loads its conventional project-owned `skai/addenda/<guide-name>-addendum.md` when present. Freeform additions/overrides may reference shared content and add local rules; wrappers remain thin and user files are protected. Report only the project-entry filename: a loaded receipt or a plain absent sentence, without per-reference announcements.
- **Independent change packages.** Requirements and UI Map packages coexist at `skai/changes/<change-id>/<type>/` and archive independently at `skai/promoted/<change-id>/<type>/`. Promotion retains canonical-write evidence for archival recovery; no-proposal UI Map conformance work uses session working documents instead of change packages.
- **Retire UI Map compatibility.** Remove the obsolete `skai-ui-map-planning` wrapper/guide and FigJam migration guide; architecture and implementation remain active. Known retired IDs are recognized for safe managed cleanup while project-owned artifacts remain intact.
- **Packaging and branding.** Ship the symmetric flat SVG SKAI logo and rounded-square app icon. App source/tests/build tooling and branding live under `internal/`; the compiled arm64 app and runtime helpers remain in `Bin/`. The Git-based bundle requires no separate user app installation/build or Developer ID/notarization setup.

**Upgrade instructions — configuration and installation**

Install the required configure wrapper and refresh managed policies/instruction blocks. Use the compiled app from the current SKAI checkout; do not copy it into host skill folders or make it a deselection candidate. Recompose copied wrapper references against the discovered checkout path. No configuration schema migration is required; schemaVersion 1/components configs from the unreleased browser prototype remain compatible.
2. **Preserve desired state.** Do not generate config for an existing default host. Preserve `skai/config.json`, `skai/config.local.json` and unrelated keys; absent project config selects all eligible components, while an explicit empty selection retains configure support. Local config contains only explicit boolean overrides; omit inherited keys. Invalid/unreadable config blocks rather than falling back to defaults.
3. **Private settings and state discovery.** Add `/skai/config.local.json` and `/skai/install-state.local.json` to the managed Git ignore block without changing its surroundings. Do not silently untrack already tracked private files. Read local state, then shared `skai/install-state.json`, then legacy `docs/skai/install-state.json`; malformed/unreadable state blocks. Follow the existing approved path migration/collision policy rather than silently moving or merging state. Seed local state from shared/legacy evidence on first use, then retain local authority and keep local effective choices/history out of shared state.
4. **Retire compatibility outputs.** Remove only verified managed `skai-ui-map-planning` wrappers under the approved update plan or component Save/apply scope. Known retired IDs in config are ignored and omitted when that scope is next saved; unknown IDs block. Repair active references to architecture/implementation and remove active references to the retired FigJam migration guide. Preserve old FigJam diagrams, canonical YAML/maps, package content/evidence and all project addenda. Never delete an unmarked project-authored lookalike automatically.
5. **Capture migration provenance.** Before removing any managed component or advancing state, persist verified inventory baselines with prior per-adapter versions/dates. A global fallback is valid only for the sole matching adapter; unknown/mixed evidence requires an artifact audit. Retain disabled/retired records and apply relevant artifact migrations from each enabled component's own last applied version, even on same-SHA re-enablement. Default installs need no component ledger until customization or removal, but still require adapter/changelog artifact checks. The optional helper's empty untracked migration list does not replace them.
6. **Preserve legacy Claude history.** For `jetbrains-claudecode`, `xcode-claudecode` or `androidstudio-claudecode`, follow the direct history procedure and Claude runbook's identity migration. The optional helper rejects those records rather than dropping evidence. Preserve their dates, versions and component history through baseline capture; incompatible evidence takes the existing audit route. Merge the canonical identity and advance success metadata only after verified reconciliation.
7. **Reconcile and verify.** Resolve both config layers and inventory each adapter's actual outputs. Refresh selected wrappers/rules, remove only verified deselected managed outputs, and preserve custom resources, unmarked lookalikes, other adapters' files and all text outside managed instruction blocks. Verified agent Save and Apply or an explicit saved-config apply request approves that component scope; unrelated migrations/unmanaged conflicts/legacy cleanup retain their separate resolutions. Report configuration drift and apply only already-authorized work; do not record stale success. Verify fresh config, inventory/content and relevant artifact migrations before recording success; failures retain baseline evidence for retry.

**Upgrade instructions — guide addenda**

1. **Refresh installed adapters.** Re-run each installed adapter after approval to copy the changed skill wrappers and refresh its managed instruction content. Existing manifest IDs, names, triggers and policy boundaries are unchanged; preserve project-owned instructions outside managed blocks.
2. **Preserve local customization.** Existing Integration settings/overrides remain intact; no automatic migration is needed. If a project wants a guide-specific rule in an addendum, move it deliberately under project-owner authorization, retaining shared settings in Integration. If an earlier unreleased setup used `skai/addendum/`, move those files to `skai/addenda/` after project-owner approval and update their shared references; stop on destination conflicts rather than overwrite user content. Leave existing `skai/addenda/` files untouched; do not generate empty files or infer a missing addendum is required.
3. **Verify discovery.** Use each needed guide's published footer name and the active host root, including when canonical artifacts live in another repository. Confirm one filename-only receipt for the project entry before guide use: `📎 ADDENDUM: <filename> — loaded` or the plain sentence `No project addendum found: <filename>.` Do not announce each referenced document. An inaccessible file/root or missing required reference must block. Verify intended overrides apply without re-approval solely for differing from guide defaults, while task instructions/project policies still hold.

**Upgrade instructions — change package layout**

1. **Discover per canonical repository.** Resolve catalog and map repositories from the app Integration doc and project documentation, including shared roots. Inspect legacy `skai/changes/<change-id>/` folders and any existing `skai/promoted/<change-id>/` folders holding type files directly. Inspect already-typed folders too: do not move them again solely because a new completion marker is absent.
2. **Determine ownership and state.** Requirements artifacts, `proposed-requirements/`, and `change-requests/requirements-*.md` belong to `requirements/`; UI Map artifacts, `proposed-ui-map.*`, and `change-requests/ui-map-*.md` belong to `ui-map/`. Requirements C7 checked means canon was written; a checked UI Map terminal promote item means the map was promoted. For partially executed artifacts, follow the owning promotion workflow's recorded progress: an
unchecked post-write requirements C7 may need mechanical confirmation/repair; a UI Map YAML write may
still need its official render before archival. Only verified canonical completion resumes archival
alone; never reset or repeat completed operations solely to finish migration. A UI Map implementation artifact with no proposal or promotion history is a conformance working document, not a promoted package.
3. **Move each type independently.** Unpromoted proposals go to `skai/changes/<change-id>/<type>/`; promoted proposals go to `skai/promoted/<change-id>/<type>/`, even when a UI Map Plan retains unchecked downstream tasks. Split mixed folders by ownership. Attribute legacy shared `evidence/` files by their citing artifacts and recorded checks; if both types cite an output, preserve a copy in each type and adjust the corresponding live output links. Block on unknown ownership or conflicting destinations instead of guessing, merging, overwriting or deleting evidence. Remove a legacy grouping directory only once empty.
4. **Relocate conformance work.** Move legacy no-proposal UI Map implementation artifacts and their owned evidence/requests to `skai/working-docs/<branch-path>/<session-name>/` in the map repository, per `Guides/Core/working-doc-conventions.md`. Recover the owning branch/session from the artifact or project context; obtain resolution if ambiguous. If an approved request is awaiting a proposed map, keep it as an active `ui-map/` package instead.
5. **Repair references and previews.** Search the app/canonical repositories and resolved repositories of linked related packages or callers for old package paths in work specs, related packages, catalog notes and package documents. Repair references only; leave sibling proposals and decisions unchanged. Repoint live incoming links and rebase links inside moved files to the same target identities. Preserve recorded commands/results; annotate historical paths with their new locations rather than rewriting execution history. Re-render proposed HTML pages at their new locations with the project override or default command from `Guides/UIMap/ui-map-guide.md`; require exit 0, a nonempty page and viewer links reaching the SKAI checkout. Preserve source YAML and retained older preview formats.
6. **Preserve and verify.** Leave canonical catalogs/maps, proposal content, item IDs, decisions, request statuses, evidence and pending Plan checkboxes intact. Record migration separately; do not fabricate C8 or new execution evidence on historical packages. Verify live links, type ownership, active/promoted placement, independent sibling state and conformance paths; a second discovery pass should find only already-migrated packages or explicitly blocked cases.
7. **Installation.** No adapter re-run is required by this change: skill wrappers and their manifest entries are unchanged, and the edited guides are read from the SKAI checkout. Apply prior release upgrade instructions first, then this layout migration; use the resulting typed paths for subsequent workflow discovery.
