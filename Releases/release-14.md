**Release documents**

**Product specs release: migration**

- 2026-10-18 **Migrating a host to this release is reviewed, not just run,** because it renames the product specs system (the requirements system until this release; the ID'd item is still a *requirement*) and changes the shape of every spec file. Work on a branch, in these named steps. Every step is safe to re-run: a move whose destination exists and whose source is gone, a conversion of an already-converted file and a mapping already applied are no-ops. Convert, never reorganize; promote nothing as part of the migration. Promoted packages are history: step 4 renames their paths and nothing in them is converted or rewritten.
  1. **Reconcile the installed components.** The adapter runbooks' normal reconciliation installs the renamed assets; this release renames in SKAI, old → new — guides: `Guides/Requirements/requirements-catalog.md` → `Guides/ProductSpecs/product-specs-catalog.md`, `Guides/Requirements/requirements-artifacts.md` → `Guides/ProductSpecs/product-specs-artifacts.md`, `Guides/Requirements/requirements-authoring.md` → `Guides/ProductSpecs/product-specs-authoring.md`, `Guides/Requirements/requirements-promotion.md` → `Guides/ProductSpecs/product-specs-promotion.md`, `Guides/Requirements/requirements-baseline.md` → `Guides/ProductSpecs/product-specs-baseline.md`; skills: `Templates/skills/skai-requirements-authoring/SKILL.md` → `Templates/skills/skai-product-specs-authoring/SKILL.md` and `Templates/skills/skai-requirements-promotion/SKILL.md` → `Templates/skills/skai-product-specs-promotion/SKILL.md`, so the installed wrappers are `skai-product-specs-authoring` and `skai-product-specs-promotion`; manifest IDs: `guide.requirements-catalog` → `guide.product-specs-catalog`, `guide.requirements-artifacts` → `guide.product-specs-artifacts`, `guide.requirements-authoring` → `guide.product-specs-authoring`, `guide.requirements-promotion` → `guide.product-specs-promotion`, `guide.requirements-baseline` → `guide.product-specs-baseline`, `skill.skai-requirements-authoring` → `skill.skai-product-specs-authoring`, `skill.skai-requirements-promotion` → `skill.skai-product-specs-promotion`, category "Requirements" → "Product specs"; addendum lookup names: `requirements-catalog` → `product-specs-catalog`, `requirements-artifacts` → `product-specs-artifacts`, `requirements-authoring` → `product-specs-authoring`, `requirements-promotion` → `product-specs-promotion`, `requirements-baseline` → `product-specs-baseline`. The adapter runbooks remove the two retired wrappers as a retirement removal under the approved plan or Save scope and install the new wrappers from the resolved set.
  2. **Skills and component history.** No manifest field maps an old ID to a new one, so the mapping is this step: a host whose `skai/config.json` lists an old skill ID (ignored as retired, dropped at the next save) gets the new ID enabled through the configuration tool (`--enable skill.skai-product-specs-authoring,skill.skai-product-specs-promotion`) rather than treated as a new component to decline; a `skai/config.local.json` override on an old ID is carried to the new ID the same way, then the old key dropped; an adapter's `componentHistory` record for an old ID is copied under the new ID (same `lastAppliedSHA`/`lastAppliedAt`, so the migration-range check still runs from the version the old wrapper was applied at) and the old record is retained as a retired record. A host with no config needs nothing: defaults select the new wrappers. A new ID already listed, overridden or recorded is left alone.
  3. **Addenda (permission-gated).** At the installation plan, for each of `catalog`, `artifacts`, `authoring`, `promotion`, `baseline`: if `skai/addenda/requirements-<x>-addendum.md` exists and `skai/addenda/product-specs-<x>-addendum.md` does not, propose moving it with `git mv`; if both exist, report both and let the supervisor merge — never overwrite, never delete. Addenda are project-owned, so the installer never performs this step on its own: it runs only on the supervisor's approval, and a shared-context repository's addenda are migrated in that repository the same way. A host that keeps the old file name silently loses the addendum, since the guides look up only the new name.
  4. **Rename in the host** (`git mv`): catalog root `skai/requirements/` → `skai/product-specs/` and its root index `skai/requirements/_requirements.md` → `skai/product-specs/_product-specs.md`; in every `skai/changes/<id>/` and `skai/promoted/<id>/`, the package type folder `requirements/` → `product-specs/`, and inside it the artifact files `requirements-authoring.md` → `product-specs-authoring.md` and `requirements-promotion.md` → `product-specs-promotion.md`, and the drafts folder `proposed-requirements/` → `proposed-product-specs/` (a change request's `proposed-product-specs/` already has the new name). Rewrite every live link to a moved path in the catalog, the design specs, open and promoted packages, work specs and the project README (the row "Product requirements" becomes "Product specs"); existing artifact titles and recorded evidence keep their text. A destination that already exists with different content is a collision: stop, never merge. Verify with a pass that finds no `requirements/` type folder, `proposed-requirements/` or `requirements-*.md` artifact under `skai/changes/` or `skai/promoted/`.
  5. **Convert.** Run `spec-tool.py convert` over `skai/product-specs/`, `skai/design-specs/` and every open package's drafts (`skai/changes/*/product-specs/proposed-product-specs/`, `*/design-specs/proposed-design-specs/` and the drafts of their change requests), a design-spec package together with the product-spec package it cites; nothing under `skai/promoted/`. Run `validate` on each root alone and on each open package projected; fix only mechanical issues (a link the converter could not rewrite, a term link) and list the rest.
  6. **Bring open packages to the new artifact forms.** In each open product spec or design spec package: remove the **Description** bullets from its change items (the diff lives on the rendered page); add `## Verification` to the authoring artifact; put the review-page link (`[Review page](product-specs-review.html)` or `design-specs-review.html`) directly under the title of the authoring artifact and of any promotion artifact; bring `## Requirement Changes` / `## Spec Changes` current; move each `change-requests/requirements-<nnn>.md` or `design-specs-<nnn>.md` to `change-requests/<nnn>/request.md`, adding a title, `## Goal` and `## Requested Changes` derived from its body and keeping its status and reviewer response. In each open design package, list under `## Assumptions and TODOs` every change request it filed against its product spec package that is still `Proposed`, for triage at the next stop (a `Proposed` request blocks design promotion). Then `render` every open package, `render-request` every request and run `check-changes` on each package.
  7. **Stop for review:** the supervisor reads the rendered pages, spot-checks converted files against their originals, triages the listed requests and resolves or defers the listed issues.
  8. **Link repair.** Re-run `validate` and `check-changes` on each open package; repair any link that no longer resolves and any change-list entry the drafts no longer match.
  9. **Stop for review:** the supervisor reviews the full diff and the recorded tool output before anything is committed.

**Spec format**

- 2026-10-18 **New guide `Guides/Core/spec-file-shape.md`** (manifest `guide.spec-file-shape`; addendum lookup name `spec-file-shape`): the one file shape product specs and design specs share. Title, intro, uncited `##` sections with an optional orientation line, `###` items carrying only the ID, a required statement, numbered rules cited with dashes (`ID-NN`, one nesting level `ID-NN-NN`), tables keyed on their first column with uncited rows, known-difference blockquotes, link definitions at the end; glossary entries as `###` headings in sentence case with every occurrence of a term linked; index lines; what the validator rejects; how the renderer diffs. Standard: `skai/refinement-reviews/spec-format-design.md`. **Migration:** the install adds the guide; catalogs and open packages are converted by the reviewed migration above.
- 2026-10-18 **New tool `Bin/spec-tool.py`** (manifest `tool.spec-tool`; standard library only): `validate` (shape, IDs, rule numbering, table keys, link definitions, glossary links, with later roots overlaying earlier ones so a package validates as its projection on the catalog), `references` (every citing file and line for an ID or rule), `link-terms` (link every glossary term occurrence), `render` (a change package's review page), `render-request` (a change request's page relative to its package), `check-changes` (the change list matches the projection's diff) and `convert` (the old shape to this one, in place). Render conventions are in its docstring; the content, authoring and promotion guides and the reviewed migration above say when each command runs.
