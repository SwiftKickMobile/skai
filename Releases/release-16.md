**Known gaps (skai#82)**

- 2026-10-20 **New reference guides `Guides/Core/known-gaps.md`** (`guide.known-gaps`) **and `Guides/Core/spec-file-gaps.md`** (`guide.spec-file-gaps`), core, no skill wrappers. `known-gaps.md` says how an agent works with a gap: a decision needed before the work ships that nobody in the work can make yet, carried as a placeholder; a decision within the author's authority is made and recorded, and one the supervisor can make now is an ordinary Discussion item. `spec-file-gaps.md` owns the footnote form for every artifact. Every Discussion-phase guide points at `known-gaps.md` with one inlined sentence. **Migration:** none.
- 2026-10-26 **Gaps in Discussion and the Decision Log** (`process-flow.md` § Structured discussion items, mirrored in the gated-workflow template and inlined in `product-specs-authoring.md`, `design-specs-authoring.md`, `design-authoring.md`, `ui-map-architecture.md`, `ui-map-implementation.md`, `work-spec-creation.md`, `work-spec-implementation.md`, the four artifact references and the three promotion guides): an open item awaiting knowledge from outside the work keeps a `- **Gap** <the placeholder alone, or "no placeholder">` sub-bullet last, with what is unknown in its Concern and nothing recording who is to answer; open gap items do not count toward the Discussion blocked gate and are named on the planned gate; an item has at most one Decision line; every Discussion-based artifact ends with `## Decision Log` (`- <ID> decided|gap|reopened — <one line>`, append-only, no dates); a resolved item stays while something current cites it, otherwise it is removed and the log keeps its record. Promotion into production requires zero open gaps (the UI Map official write included); promotion into another open package carries them into it. `spec-tool.py check-changes` fails when the log and the Discussion disagree (missing log once items exist, log not last, a malformed entry, an entry naming no item, an item's last entry not matching its state, two Decision lines, a checked item with a Gap line, a change entry citing a `D#` the Discussion lacks; entries for removed items are allowed). **Migration (re-runnable):** for every unpromoted Discussion-based artifact (`skai/changes/*/product-specs/product-specs-authoring.md`, `*/design-specs/design-specs-authoring.md`, `*/design/design-authoring.md`, `*/ui-map/ui-map-architecture.md` and `ui-map-implementation.md`, every work spec design under `skai/working-docs/`), if it has no `## Decision Log`, append one as the last section before the link definitions, seeded with `- D<n> decided — <its Decision text>` for each checked item in artifact order; an artifact that already has one is left alone. A Gap line in an older wording (`none; waiting on …`, `no placeholder; waiting on …`) still parses and is reworded at the package's next reopen.
- 2026-10-24 **Gap footnotes, one form for every artifact** (`spec-file-gaps.md`; `spec-file-shape.md`, `product-specs-authoring.md`, `product-specs-artifacts.md`, `design-specs-authoring.md`, `design-authoring.md` point at it): a placeholder in a spec draft or a design change list entry is marked `[^n]`, numbered by first use, with `[^n]: **Gap:** <owning item>. Placeholder: <the provisional answer this place builds on>` under the item or entry (`[^n]: **Gap:** <owning item>.` when there is no placeholder). The owning item is the item where the question was raised, this artifact's `D<n>` or scoped (`base D04`, `product specs D21`), never one that merely inherits it; the question is not repeated. Canon carries no footnote. `validate` pairs markers and definitions, requires numbering by first use, and rejects a duplicate label, a definition off the form or outside an item, one after a known difference, any footnote in canon, and the older `D<n> — <question>. Placeholder:` form; `check-changes` pairs footnotes naming this artifact's items with its open gap items; a requirement is modified when its footnote set differs from the base's. **Migration (re-runnable):** in every unpromoted spec package's drafts, rewrite each definition `[^n]: **Gap:** D<n> — <question>. Placeholder: <text>` to `[^n]: **Gap:** D<n>. Placeholder: <text>` (`[^n]: **Gap:** D<n>.` without a Placeholder clause), then renumber each file's labels by first use; a definition already in the form is left alone. Footnotes naming an inheriting item (a base's "Inherits D<n>" item) are re-pointed at the originating item when the package is next brought to conformance.
- 2026-10-23 **Inherited gaps are footnotes, not Discussion items** (`known-gaps.md` rules 3, 5–7; `design-authoring.md` § Discussion and § Design Changes; `design-promotion.md` readiness 1 and `C3`): a package's own gap is an unchecked item with a Gap line; a gap inherited from an input is a footnote on what stands on its placeholder, naming the owning item. In a design change list the footnote goes only on the first entry whose change rests on the placeholder. **Migration (re-runnable):** for every unpromoted design package, each Discussion item that only inherits an input's gap ("Inherits D21 of the product specs …") becomes a footnote on the first entry resting on its placeholder; the item is removed and its log entries kept; items the design raised itself stay. An artifact with no inheriting items is left alone.
- 2026-10-28 **Gaps on Figma change pages, once each** (`figma-designer-guide.md` § Gaps and the canvas ordering rule; one sentence each in `design-authoring.md` and `design-promotion.md` `C1`): each open gap gets one Dev Mode annotation across the package's drawings, on its placeholder node in the first frame drawing it in canvas order (down a column, then across), in the file's annotation category `Gap` (yellow, created if missing), reading three lines: `<owning item ID>: <the question>`, `Placeholder: <what is drawn>`, `Owner: <owning artifact's path under skai/changes>`. It moves when canvas order changes and goes when the gap closes; production carries none. **Migration (re-runnable):** for each open design package with gap annotations in an older form (`D<n> — <placeholder>`, or the three-line `Gap:` form), rewrite each gap's first annotation to the new text and category and delete its later annotations. A package already in the form has one annotation per gap and is unchanged.

**Design packages and design change requests (skai#95, skai#99)**

- 2026-10-23 **A design package authors against a base; a change request is a package whose base is another open design package** (`design-authoring.md`, `design-promotion.md` rewritten; `figma-designer-guide.md` Pages): a request lives at `<base>/change-requests/<nnn>/` with the full package layout and may nest; it draws in a section `CR-<nnn> — <name>` on the base's change page holding only added or changed frames (a changed screen as a copy); promotion folds it into the base (frames into the base's sections by name, entries appended to the base's Design Changes ending with their request number, open gaps carried into the base) and archives it at `<base>/promoted-change-requests/<nnn>/`. No roles: whoever runs a workflow on a package authors it. With no access to the design tool, the supervisor may rule that no mockups are drawn; the change list then stands in for the drawings and such entries never promote into production. Completion reconciles the inputs: the agent files a change request through each affected input's own process, with drafts, or tells the supervisor what the input needs; promotion readiness blocks on any unruled request. **Migration:** none; requests are only created by the new guide.
- 2026-10-24 **Design Changes is a live typed list that walks the canvas** (`design-authoring.md` § Design Changes; `design-promotion.md` `C1`–`C3`; `figma-designer-guide.md` Pages, Screen pages, Components): entries `- V<n> <add|modify|remove> <screen|state|component>: <identity>` with a **Description** (what changed, in the product's words, never sample data or measurements) and a **Justification** (the reason in a sentence, then its source), kept current with the drawings; grouped under `### <screen>` headings in canvas order, one entry per frame, several changes to one frame as numbered sub-changes (`- **01** <text> — <justification>`); a `remove` entry keeps the base design's name. "Approved" is gone: the Review gate's `next` is the approval. Change pages and request sections hold one Section per screen plus `Components`; the concept letter lives in the page name. **Migration (re-runnable):** for every unpromoted `skai/changes/*/design/design-authoring.md` whose `## Design Changes` is in the old one-line form (`` `screen` — new|changed: … ([draft](link)) ``), rewrite each line as a `- V<n>` entry in artifact order (`new` → `add screen` or `add state`, `changed` → `modify screen`; identity the frame's name linked to the same target; Description the line's text; Justification `Supervisor input` unless the Discussion names the decision), then group the entries under `###` headings in the order the page shows. An artifact already in the form is left alone. Regroup the change page itself into one Section per screen when the package next reopens.
- 2026-10-23 **New tools `Bin/design-tool.py`** (`tool.design-tool`) **and `Bin/figma-page-check.js`** (`tool.figma-page-check`), core. `design-tool.py render --authoring FILE [--specs ROOT ...] [--out FILE]` writes `design-review.html` beside a design artifact: the package card, Discussion and Design Changes in the spec pages' shell, headings and sub-changes, gap footnotes as one-line notes with the owner's chip; the authoring guide renders on every material change and before every gate. `figma-page-check.js` is a `use_figma` script reporting a page's or Section's structure breaches against the Figma guide's canvas rules; authoring runs it before the Review gate and promotion's `C1` runs it first. Tests under `internal/tests/tools/`. **Migration (re-runnable):** render every unpromoted design package once (`python3 <skai>/Bin/design-tool.py render --authoring skai/changes/<id>/design/design-authoring.md --specs <catalog> [--specs <product-specs drafts>]`) and commit the page beside the artifact.

**Working documents (skai#92)**

- 2026-10-21 **Working documents live beside the artifact they serve, and are committed** (`Guides/Core/working-doc-conventions.md`; path formulas in the work-spec, UI Map implementation, ticket-filing, process-refinement and unit testing guides; the four package artifact guides and the promotion guides): a document serving a change package goes in `skai/changes/<change-id>/<type>/working-docs/` in the package's canonical repository and archives with it; any other goes in `skai/working-docs/<session-name>/` (no branch folder). Hosts commit them; the installer's managed `.gitignore` block now holds only `/skai/config.local.json` and `/skai/install-state.local.json`. Output captured to verify a build or test goes to a scratch root outside the repository (default `/tmp/skai/<session-name>/`, or the root `skai/integration.md` names); the evidence line is the record. The Integration template gains a **Scratch root** field.
- 2026-10-21 **Migration** (re-runnable: a document already placed, output already dispositioned or a line already removed is a no-op):
  1. **Re-run the adapter runbooks.** They drop `skai/working-docs/` from the managed `.gitignore` block and add the Scratch root field to `skai/integration.md`'s `required-values` block with its default. Nothing is committed by the update.
  2. **Discover** every session folder under `skai/working-docs/<branch-path>/`, and under a top-level `working-docs/` where one exists, in the app repository and each canonical repository the README links; every folder already at `skai/working-docs/<session-name>/` or in a package's `working-docs/`; and every place the old guides sent captured output (a work spec's `evidence/`, a package type folder's `evidence/` holding UI Map build output). This list is the inventory.
  3. **Classify and stop.** For each entry: (a) a document to relocate, with its destination (the package it serves, `skai/promoted/<change-id>/<type>/working-docs/` for a promoted one, or `skai/working-docs/<session-name>/` when it serves none; a folder serving several packages is split by document, notes serving two go with the upstream one); (b) captured build or test output, proposed for removal or for the scratch root, never a committed place (package `evidence/` holding promotion check output stays); (c) already placed. List the proposed moves and dispositions and stop for the supervisor's approval; an unclear association is the supervisor's call.
  4. **Move and disposition** as approved: `git mv` for tracked files and `mv` otherwise within a repository; across repositories, copy and remove, each side reviewed in its own repository. An existing destination is a collision: stop and report it. Remove a branch or top-level folder only when it is empty.
  5. **Repair links** into moved documents and the relative links inside them, keeping every target the same.
  6. **Verify against the inventory**, then the supervisor reviews and commits the newly visible working documents.
