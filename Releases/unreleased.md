- 2026-11-07 **Route enums live in their own files beside the view model** (skai#81; `Guides/UIMap/ui-map-swiftui.md` and `ui-map-compose.md` § Scene file layout, `ui-map-compose-placeholders.md` § Route enums and § View models and DI): each nav, tab or child route is a `<Scene><Kind>Route` file, and a scene's modal destinations share one `<Scene>ModalRoute` file (the Compose `ModalRoute` sealed class, or the SwiftUI sheet, cover and popover enums together), instead of all of them at the top of `<Scene>ViewModel`. - 2026-11-10 **Placeholder tabs keep their screens across redraws and select through the scene's tab route enum** (skai#57, skai#131; `Dev/Swift/Sources/SKAISwiftUI/PlaceholderScene.swift` and `PlaceholderTab.swift`, `ui-map-swiftui-placeholders.md` § tab): `PlaceholderTab` took a new random identity each time its scene was built, so every redraw of the host rebuilt each tab's content and lost its state (view model, pushed screens, open sheets). `PlaceholderTab` now requires `route:`, any `Hashable` value, the tab's case of the scene's tab route enum, and takes its identity from that value. A tabbed `PlaceholderScene` takes `selection:`, a binding to the view model's current tab route, and matches it by `==`. In debug builds, a scene stops when a tab's route is of another enum. **Migration:** none; no host code uses tabbed placeholders yet.
- 2026-11-10 **A SwiftUI route's identity is its whole value** (skai#131; `Guides/UIMap/ui-map-swiftui.md` § Route enums and every route enum example, `ui-map-swiftui-placeholders.md` nav and child examples): every route enum, nav, modal, child and tab, is `Identifiable, Hashable` with `var id: Self { self }`, replacing the stable string `id` per case. A route's associated values are part of its destination's identity, so setting a route to a new value (`.detail(itemID: "b")` after `.detail(itemID: "a")`) presents a new screen; with a per-case `id`, SwiftUI kept the old screen and its state. Nav and child destination views take `.id(route)`: a view's view model lives as long as the view, so without it a pushed or child screen keeps the view model built from the old value. Placeholder scaffolds wire it the same way, so the routing feature work builds on already has it. **Migration:** none at update; existing route enums are unchanged, and new route enums follow the rule.

- 2026-11-11 **A UI Map can mark screens and routes by form factor** (skai#67; new `Guides/UIMap/ui-map-form-factors.md`, `ui-map-guide.md`, `ui-map-implementation.md`, `Bin/ui-map.schema.json`, `Bin/ui-map-render.py`, `Bin/ui-map-viewer.v1.js`): a map may declare its own `form_factors` (phone, tablet, …). A screen not on every form factor declares `form_factor` on its definition, a route used on only some is a `to:` entry, and `modal_style` may be a map from form factor to style. The renderer checks that markings agree with the routes and says what to declare; its form-factor errors point to the new guide, which agents read only when the map declares `form_factors` or the work adds a difference. How code reads a form factor is the project's own pattern, reached from `skai/addenda/ui-map-form-factors-addendum.md`; when it's missing, implementation stops and the agent adds it with the supervisor. A scene reached by several routes from one parent no longer needs `primary_parent`. The viewer's side panel shows a per-form-factor modal style; marking routes and filtering by form factor in the viewer come later. **Migration:** none for maps without form factors.
