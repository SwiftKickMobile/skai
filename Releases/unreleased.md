**Working documents (skai#92)**

- 2026-10-21 **Working documents live beside the artifact they serve, with no branch folder** (`Guides/Core/working-doc-conventions.md`; path formulas in `work-spec-creation.md`, `work-spec-implementation.md`, `ui-map-implementation.md`, `ui-map-implementation-artifacts.md`, `ticket-filing.md`, `process-refinement-guide.md` and the three unit testing guides): a document serving a change package goes in `skai/changes/<change-id>/<type>/working-docs/` in the package's canonical repository; any other goes in `skai/working-docs/<session-name>/` (the `<branch-path>` segment is gone; a work spec serves a change, not a package, and is found at `skai/working-docs/<spec-name>/`). A document serves a package when it exists because of that package (source notes, reviews, audits, scripts); notes serving two packages go with the upstream one and are linked from the other.
- 2026-10-21 **Package `working-docs/` archives with the package** (`product-specs-artifacts.md`, `design-specs-artifacts.md`, `ui-map-architecture-artifacts.md`, `ui-map-implementation-artifacts.md`, `design-authoring.md`; `product-specs-promotion.md`, `design-specs-promotion.md`, `design-promotion.md`, `ui-map-implementation.md` § Archive the package): the folder is part of the type folder that promotion moves to `skai/promoted/<change-id>/<type>/`; `spec-tool.py` reads only drafts and the authoring artifact, so it ignores the folder.
- 2026-10-21 **Working documents are committed** in host repositories (skai's own stay ignored; its refinement records live in `skai/refinement-reviews/`). The installer's managed `.gitignore` block now holds only `/skai/config.local.json` and `/skai/install-state.local.json`; an update removes the `skai/working-docs/` line from an existing block (`Install/*/install-update-*.md`, `Install/component-selection.md`).
- 2026-10-21 **Output captured to verify a build or test goes to a scratch root outside the repository** (a build's deliverable is not captured output). Command captures, result bundles, extracted results and screenshots go under `/tmp/skai/<session-name>/` (the change ID for package work) unless `skai/integration.md` names another root; the evidence line names the command, the result and the scratch path and is the record (output need not survive). Work spec implementation no longer persists failure output under `<spec-name>/evidence/`, UI Map implementation no longer persists build output under `evidence/`, and the unit test writing guide's test-output files move to the scratch root. The Integration template's evidence section gains a **Scratch root** field with that default (`Templates/docs/skai/integration.md`), and `Install/integration-doc-install-update.md` adds a template field a host's form lacks.
- 2026-10-21 **Migration** (re-runnable: a document already at its approved place, output already dispositioned, or a line already removed, is a no-op):
  1. **Re-run the adapter runbooks.** They drop `skai/working-docs/` from the managed `.gitignore` block and add the Scratch root field to `skai/integration.md`'s `required-values` block with its default. A host that keeps output elsewhere replaces the default with a root outside the repository. Nothing is committed by the update.
  2. **Discover** every session folder under `skai/working-docs/<branch-path>/`, and under a top-level `working-docs/` where one exists, in the app repository and in each canonical repository the README links (a session folder is the folder holding the documents; the branch folders above it, and the top-level folder, are what goes away). A folder already at `skai/working-docs/<session-name>/` or in a package's `working-docs/` is an entry too: its path says nothing about its contents. So is every place the old guides sent captured output: a work spec's `evidence/`, and a package type folder's `evidence/` where UI Map implementation kept build output (its promotion check output stays). The list is the migration's inventory; every entry gets one of the classifications below.
  3. **Classify and stop.** For each entry: (a) a document to relocate, with its destination: the `working-docs/` folder of the package it serves (`skai/changes/<change-id>/<type>/working-docs/`, or `skai/promoted/<change-id>/<type>/working-docs/` for a promoted package, in the package's canonical repository), or `skai/working-docs/<session-name>/` when it serves none (a folder whose documents serve different packages is split by document; notes serving two packages go with the upstream one, and the other links them); (b) captured build or test output (`evidence/` folders of work specs or UI Map runs, `*-test-output.txt`, `.xcresult` bundles, extracted results, screenshots), proposed for removal or for the scratch root, never for a committed place; package `evidence/` folders holding promotion check output are not output and stay; (c) already placed: a document whose contents pass the same association test at its current location, with its workflow subfolders, so it needs no relocation. List the proposed moves and output dispositions together and stop for the supervisor's approval; an unclear association or identity is the supervisor's call, never a guess.
  4. **Move and disposition** as approved: within one repository, `git mv` for tracked files and `mv` otherwise; into another repository, copy to the destination and remove the source, each side a change reviewed in its own repository. A destination that already exists is a collision: stop and report it; never overwrite or merge. Remove a branch folder or top-level folder only when it is empty. Evidence lines that link removed output stay as written history.
  5. **Repair links** into moved documents (work specs, package artifacts, other working documents) and the relative links inside them, whose meaning changed with the move, keeping every target the same.
  6. **Verify against the inventory:** each (a) entry is at its approved destination, each (b) entry has its approved disposition, each (c) entry is not relocated (link repair under step 5 may still have edited it), and no unresolved legacy entry remains; `git status` is for reviewing the resulting changes, not the inventory. Then the supervisor reviews and commits the newly visible working documents.
**Glossary alternate terms (skai#93)**

- 2026-10-21 **Glossary entries may carry an Also called note** (`Guides/Core/spec-file-shape.md` § Glossary File, its validator list and diff keys; `product-specs-catalog.md` § Glossary now says each entry's paragraph, not the whole entry, ends with the governing links): one blockquote after the definition paragraph, last in the entry, `> **Also called:** <term> (<who uses it>); <term> (<who uses it>).`, naming what others call the term so an agent reading inputs recognizes it. Alternates are never linked and never used in spec prose; the entry's term stays the only name the specs use.
- 2026-10-21 **`spec-tool.py` parses, checks and renders the note.** Every blockquote in a glossary file is read as a note; `validate` rejects one outside an entry, a note with no definition before it, a second note, one off the form (a link in it included, as is an address Markdown links on its own: `://`, `mailto:`, `www.`, an email address) and any line after it in the entry; a definition that merely contains "Also called" is not the note. `render` shows it as a muted callout under the definition and in the term's popover, and diffs it apart from the definition, so a changed or added alternate makes the entry modified without marking the definition reworded; an entry moved to another glossary file shows as added there, its definition and note diffed against its old home, which it names (`check-changes` then wants a modify entry for it, and checks a moved entry's note too, against the catalog under any `--base`). `link-terms`, the unlinked-term check and `references` ignore alternates. **Migration:** none expected; no canonical glossary carries the note. Because any blockquote in a glossary file is now read as a note, run `validate` on the catalog after the update (re-runnable): a glossary blockquote it reports was never part of the shape; stop and show it to the supervisor, who decides whether it becomes the note or moves into the definition. Re-render an open package only if its glossary gains a note.
