- 2026-11-11 **A change request is a folder that can change several document types, and the agent confirms whether work is a request** (skai#108, skai#129; `Guides/Core/change-requests.md`, `known-gaps.md` rule 2, the product specs, design specs and design artifacts, authoring and promotion guides, `figma-designer-guide.md`, README, `internal/maintenance/change-packages.md`; `spec-tool.py`, `design-tool.py`, `figma-page-check.js`).
  - **Layout.** A request is `skai/changes/<change-id>/changes/CR-<id>/` holding one sub-package per type it changes (`CR-01/product-specs/`, `CR-01/design/`), each in its type's layout with only the files it changes. A promoted sub-package moves to its parent's `promoted/CR-<id>/<type>/`. A request against a request nests: `changes/CR-01/changes/CR-01-01/`. IDs are two digits, the parent's next free number across its open and promoted requests of every type. The old `<base>/change-requests/<nnn>/` and `<base>/promoted-change-requests/<nnn>/` folders are gone, and the tools read only the new layout.
  - **Base.** Each sub-package builds on the nearest package of its type up the chain (the parent request's, its parent's, …, the change's own), else production. A request part with no package of its type above it is a request against production: it is drawn in a request Section on a change page and archives under `skai/promoted/<change-id>/`.
  - **One promotion rule for any base.** Promotion folds a sub-package into its base and moves it to its parent's `promoted/`, or into production under `skai/promoted/<change-id>/`, taking along the promoted sub-packages folded into it, paths kept. A request's sub-packages promote together unless the supervisor asks otherwise. When a request's last sub-package moves, its open requests move to its parent's `changes/`, IDs kept, first inputs repointed. Production readiness blocks on another open request part of the same type in the change and on open items or gaps in that type's promoted parts; another open request part or a pending input outcome waits at the standard blocked gate instead of returning the package to authoring.
  - **Self-references use the new ID:** a folded entry's provenance ends `; Change request: CR-01 R5` (`S5`, `V5`); a decided base item ends `(CR-01)`; a link label reads `[D5][CR-01 D5]`; a page's top bar reads `<title>: <change-id> | CR-01 | …`; a request's Figma Section is `CR-01 — <name>` (nested `CR-01-01 — <name>`).
  - **Is it a request? (skai#129).** When the supervisor's words don't say whether work edits a package directly or is a change request, the agent asks before creating or reopening anything. No guide picks a route to another package: the product specs references sweep, design specs requirements gaps and `known-gaps.md` rule 2 (an inherited placeholder that seems wrong) defer to the supervisor's choice in `change-requests.md` rule 8.
  - **Migration (re-runnable; reviewed, not just run).** Scope: active base packages (`skai/changes/<change-id>/<type>/`) in the host and in every repository the README or a project addendum links for change packages. Archived packages under `skai/promoted/` are never touched. A `request.md` from before requests were packages stays where it is as a record.
